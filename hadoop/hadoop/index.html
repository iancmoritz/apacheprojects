Apache Hadoop — WebAssembly

starting…
Nothing here runs on a server. Apache Hadoop 3.3.6 is running in this tab on a JVM compiled to WebAssembly: in HDFS mode a real NameNode with an fsimage and an edit log and a real DataNode with block files, and in local mode Hadoop’s own MapReduce — LocalJobRunner, real splits and real Counters — over Hadoop’s LocalFileSystem. Every path, block, split and counter on this page comes back from Hadoop’s APIs. The two do not yet work together: see what a tab cannot do.

    What a tab cannot do
    
          
      
            
    • 
              One run per page load. With MiniDFSCluster running,
              CheerpJ never returns from a second call into Java — not even from a method that
              only returns a string — and MiniDFSCluster.shutdown, which would end
              the first call cleanly, hangs finalizing the edit log. So a run is a single call that
              starts the NameNode and DataNode and plays every command against them, and running again
              means a reload: a new JVM, a newly formatted namespace, and the boot paid again.
            
      • 
            
    • 
              No listening sockets. Hadoop’s RPC, the DataNode’s data
              transfer protocol and Jetty all get an in-process TCP stack (a
              SelectorProvider in java/…/net/), so the NameNode and
              DataNode really do talk to each other over sockets — but nothing outside the tab
              can reach them, so the NameNode web UI is unreachable.
            
      • 
            
    • 
              No native code and no subprocesses. There is no
              libhadoop.so, so checksums, NativeIO and the native codecs are
              off; du, df and ls -ld are replaced by Java
              implementations, and HDFS permission checks are disabled because the tab has no OS user.
            
      • 
            
    • 
              MapReduce is Hadoop’s LocalJobRunner. Real
              Mapper, Reducer, InputFormat, splits, task reports
              and Counters, but there is no YARN in the tab, so tasks are threads rather
              than containers.
            
      • 
            
    • 
              An interrupt that CheerpJ does not deliver. A thread waiting in an
              untimed Condition.await is not woken by Thread.interrupt()
              here, and that is how MapTask ends its spill thread — so no map task
              could ever finish, and the job stopped after “Finished spill 0”. The build
              rewrites Hadoop’s interrupt() call sites to add an
              unpark, which is what makes the WordCount above complete.
            
      • 
            
    • 
              MapReduce and HDFS do not run in the same tab. The job finishes over
              Hadoop’s LocalFileSystem (local mode) every time; submit it with the
              MiniDFSCluster up and roughly five seconds later every thread in the JVM stops —
              the DataNode’s and NameNode’s own select loops included, which the virtual
              network’s trace shows going quiet together — and the tab never comes back.
              The HDFS commands above all complete in that same run, right up to the submit, and every
              wait in the virtual network is bounded, so it is CheerpJ’s scheduler rather than a
              lock Hadoop is holding. Not the interrupt bug above either: it happens identically with
              that shim off (?unpark=0), with the shim never compiled in, and with the
              daemons’ pools cut to one handler each.
